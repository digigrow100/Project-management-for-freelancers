## Protocol

An existing admin job may be prepared through same-origin `POST /api/hosting-operator/dispatch` with `{job_id,request}`. The verified admin/MFA session must match both job requester and enrolled mapping actor. `request` has exactly `operation`, `idempotency_key` (job UUID), `payload`, `auth` (`issued`, canonical base64url Ed25519 `signature`). Sign the existing host `controlplane.signing` message locally; private keys never reach this endpoint. Provision/create accepts a bounded ASCII name; suspend/resume accept the enrolled host project ID; deploy accepts project, scope and exact 40-hex commit. The host's enrolled repo/workflow/artifact checks and separate activation approval still apply. Old notes, moving branches, rollback, service cancellation, project deletion and arbitrary payloads are excluded.

Owner enrollment binds server/client/service IDs, host tenant/subject, requester and project. Both sides independently hold these mappings. A successful project.create Intake receipt binds its returned ID; neither portal UUID nor user note becomes a guessed host project ID. Mapping changes/revocation are owner enrollment work, not client actions.

The VPS initiates HTTPS POSTs only to a fixed enrolled origin and `/api/hosting-operator`. `{server_id,claim_id}` retrieves at most one delivery. `{server_id,receipt}` acknowledges it. Token is a 32+ byte cryptographically random base64url bearer, stored root-private on the VPS; only domain-separated SHA256 is stored in `operators.token_sha256`. This is not a Supabase key. RPCs verify credential/enabled state within each transaction. Portal machine route has a separate `HOSTING_OPERATOR_TRANSPORT=approved` gate; it is absent by default. No settings or credentials are enabled/generated by the migration.

Each delivery contains the exact signed request JSON and server/client/service/tenant/subject, a five-minute expiry and exact UTF-8 body digest. Atomic claims never automatically requeue. A persisted host claim ID survives lost replies. Interrupted receiving state stops as recovery_required. Queued receipt acknowledgment precedes final publication. Final receipts must match delivery/claim/server/body/local ID; duplicate identical receipts are safe. Mismatches, revoked server access or backward transitions fail. Cancellation locks the delivery, rejecting already claimed jobs and removing unclaimed deliveries from eligibility.

## UI and deployment limits

Admin Operations shows delivery state and observation separately. `queued` means imported into local SQLite; `applied` means the existing host Intake accepted an intent. Neither indicates provisioning, runtime health, backup acceptance or a deployed website. Client service labels are unchanged. The manual signed request endpoint is implemented; no browser key enrollment/signing UI or automated polling timer is added in this stage.

The additive migration is tested in PGlite 0.5.10 and has no browser table/RPC grants. It has NOT been applied to live Supabase. Do not merge/deploy this branch as an enabled production connection. Before a later approved rollout, apply the reviewed migration, retain the global flag absent, enroll disabled server mappings, and verify role denials. No VPS installation or activation occurs without the owner's exact approval.
